## Правило завершения сессии

**В конце каждой сессии разработки обязательно:**

1. **Обнови `PLAN.md`** — отметь выполненные задачи (`[x]`).
2. **Создай/обнови `.planning/prompt-for-next.md`** — сообщение для себя на следующую сессию. В нём должно быть:
   - **Контекст:** что сделано в этой сессии
   - **Следующие шаги:** что делать дальше, на чём остановились
   - **Название коммита** для текущей сессии (на русском, в формате: `тип: краткое описание`, например `init: создан PLAN.md, README.md, обновлены .clinerules`)
   - **Предупреждения/заметки:** что нужно учесть в следующей сессии, какие есть нерешённые вопросы
3. **Обнови версию сборки в ДВУХ файлах (синхронно, одинаковое значение!)**:
   - `packages/frontend/src/app/config/index.ts`:
     - `VERSION` — увеличь на 1 (формат `major.minor.patch`; сейчас `2.22.0`: major=2 — первое большое обновление, minor=22 — номер сессии)
     - `ASSEMBLY_DATE` — текущая дата в формате `YYYY-MM-DD`
   - `packages/backend/src/app/config/index.ts`:
     - `VERSION` — то же значение, что и во фронте. Бэкенд сверяет заголовок `X-Client-Version` с этим значением в `CheckVersionInterceptor` (NestJS): при рассинхроне клиенты получают 409 Conflict и перезагружаются. Если обновить только фронт и забыть бэкенд — клиенты застрянут на старой версии.
4. **Название коммита** записывай в `.planning/prompt-for-next.md` в поле `## Коммит`.
5. **Фиксируй «долгоживущие» сведения в постоянной документации.** Всё, что должно пережить перезапись `.planning/prompt-for-next.md` (инфраструктура деплоя, пути юнитов/конфигов/секретов, причины архитектурных решений, договорённости об окружении), записывай в `README.dev.md` (или тематический `.md` в `.planning/codebase/`). `.planning/prompt-for-next.md` — только краткое переходящее напоминание для следующей сессии.

**В начале каждой сессии:**

1. Прочитай `.planning/prompt-for-next.md` — чтобы восстановить контекст
2. Прочитай `PLAN.md` — чтобы понять текущий статус

## Правило завершения задачи

**После каждого изменения в коде обязательно выполняй:**

```bash
npm run lint           # ESLint, max-warnings 0
npm run test -w packages/backend    # Все тесты бэкенда
npm run test -w packages/frontend   # Все тесты фронтенда
```

Задача считается завершённой, только когда все три команды проходят без ошибок.

## Стандарты кода

### Общие правила

- **Язык:** TypeScript (strict mode) — никакого `any` без крайней необходимости.
- **Именование:** используй только термины из глоссария проекта (см. ниже). Не выдумывай синонимы.
- **Формат кода:** ESLint + Prettier, проверка перед каждым коммитом (Husky + lint-staged).
- **Комментарии:** на русском языке, описывай «почему», а не «что».
- **Структура папок:** по фичам или слоям, в рамках монорепозитория (`frontend`, `backend`, `shared`).

### Frontend (React / Vite)

- Функциональные компоненты, хуки.
- Управление состоянием: Redux Toolkit (локальное), React Query (серверное — в будущем).
- Обработка состояний компонентов: **loading, empty, error, disabled** — всегда.
- Доступность (WCAG AA): семантическая вёрстка, клавиатурная навигация, контрастность.
- Адаптивность: mobile-first, отдельные варианты компонентов для desktop/mobile при разном функционале.
- Lazy loading: страницы (React.lazy + Suspense), компоненты (React.lazy), изображения (loading="lazy").

### Backend (Node.js / Koa)

- Все данные от клиента валидируются на бэке (AJV).
- Единый формат ошибок API (см. раздел «Контракты API»).
- Rate limiting на эндпоинтах.
- Middleware верификации Firebase-токена на каждом защищённом эндпоинте.

### База данных (Firestore)

- Составные индексы для частых запросов.
- Security Rules: минимально необходимые права для каждой роли (Пользователь, Админ, Супер-админ).

## Недопустимые действия (строгие запреты)

1. **Не упрощай бизнес-логику.**

2. **Не меняй стиль дизайна.** Не заменяй на Material Design, Tailwind UI по умолчанию и другие стандартные библиотеки стилей. Не жертвуй читаемостью ради стиля.

3. **Не выдумывай свои названия** для сущностей, полей, статусов, маршрутов. Используй только то, что указано в глоссарии и спецификации.

4. **Не игнорируй состояния компонентов.** Каждый интерактивный элемент должен иметь loading, empty, error, disabled.

5. **Не пропускай server-side логику.** Всё, дашборда — проверяется на бэке, даже если фронт уже проверил.

6. **Не допускай раскрытия внутренних деталей в продакшене.** Все ошибки логируются на бэке, клиенту — обобщённое сообщение.

## Ключевые доменные термины (обязательно использовать точно)

Используй эти термины в коде, комментариях и документации. Не заменяй их синонимами.

### Сущности и поля

- `User` / `Company` / `Dashboard` / `Partner` / `Template` / `Transaction`
- `Super admin` / `Developer` / `Owner` / `Employee`

### Коллекции Firestore

- `users` — пользователи системы
- `companies` — компании (организации)
- `dashboards` — дашборды и их view
- `templates` — шаблоны дашбордов
- `partners` — партнёры реферальной программы
- `transactions` — транзакции (финансовые операции)
- `docs` — документы (политики, оферты)
- `logs` — логи действий

### Маршруты (страницы)

- `/` — главная (редирект на дашборд или логин)
- `/login` — вход
- `/signup` — регистрация
- `/dashboard` — дашборд (редактор и просмотр)
- `/company` — управление компанией
- `/company-profile` — профиль компании
- `/user-profile` — личный кабинет пользователя
- `/policy` — политика конфиденциальности
- `/demo` — демо-режим
- `/not-access` — нет доступа (403)
- `/not-found` — страница не найдена (404)

### API эндпоинты (базовый URL: `https://rhy.thm.su/api`)

- `POST /api/auth/login/byEmail` — вход по email
- `POST /api/auth/signup/byEmailStart` — начало регистрации (по email)

- `POST /api/auth/login/resetEmailPassword` — сброс пароля
- `GET /api/user/getAuth` — получение данных пользователя и компании
- `POST /api/user/update` — обновление данных пользователя
- `POST /api/user/logout` — выход
- `POST /api/company/update` — обновление данных компании

- `POST /api/dashboard/bunch/get` — получение групп элементов дашборда
- `POST /api/dashboard/view/createGroupItems` — создание элементов дашборда
